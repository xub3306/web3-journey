# 01 · 链原理 + 交易生命周期(中文精讲)

> 目标:搞懂"一笔交易从你点确认到最终落链,中间发生了什么"。
> 这是面试必问、也是 debug 的地基。看完能回答:交易为什么会失败?gas 花在哪?pending 卡住为什么?

---

## 1. 区块链的本质:一台人人可验证的状态机

一句话:**区块链 = 一个全局状态 + 一堆待处理的交易 + 所有节点共同维护的一份账本。**

- **状态(state)**:所有账户余额 + 所有合约的代码和存储。这是"当前真相"。
- **交易(transaction)**:一条"请把状态从 A 改成 B"的指令。
- **区块(block)**:一批交易打包在一起,附上前一个区块的哈希 → 形成链。
- **矿工/验证者(validator)**:决定哪些交易进哪个区块、按什么顺序。

关键点:**状态只能通过交易改变**。没有任何"后台直接改数据库"的操作。这是链上开发和 Web2 最大的区别。

> 测试视角:链上没有"数据脏了手动修一下"。**写错一次,不可逆**(除非合约专门设计了回滚/升级)。

## 2. 账户模型:EVM 只有两种账户

| | EOA(外部账户) | 合约账户(Contract) |
|---|---|---|
| 谁控制 | 私钥持有人 | 代码 |
| 有代码吗 | 没有 | 有 |
| 能主动发起交易吗 | ✅ 能 | ❌ 不能(只能被调用) |
| 地址怎么来 | 公钥哈希 | 创建者地址 + nonce 推导 |

**每个账户都有 4 个字段:**

| 字段 | 含义 |
|---|---|
| `nonce` | 该账户**发出过**的交易数。EOA 用它防重放、定序;**合约用它决定它创建的下一个合约地址** |
| `balance` | 余额(wei,1 ETH = 10^18 wei) |
| `code` | 合约字节码(EOA 为空) |
| `storage` | 合约的持久化存储(EOA 为空) |

⚠️ **坑点**:
- nonce 必须**连续**。你发了一笔 nonce=5 的交易卡住了,后面 nonce=6 的也一起卡(因为不能跳号)。想取消就**用同一个 nonce、更高的 gas** 发一笔空交易顶掉它。
- 合约不能自己"醒来"执行 —— 必须有 EOA 触发它。所谓"定时任务"是靠 keeper / 外部调用者。

## 3. 一笔交易的字段(必须背下来)

```js
{
  nonce: 5,                    // 这个账户发过的第几笔(防重放、定序)
  to: "0xabc...",              // 目标地址(EOA 转账 or 调用合约)
  value: 1000000000000000000n, // 转多少 wei(转给合约也常用)
  data: "0xa9059cbb...",       // 调用数据:函数选择器 + 参数
  gasLimit: 21000n,            // 你最多允许消耗多少 gas
  maxFeePerGas: 30000000000n,  // 每 gas 你最多付多少(EIP-1559)
  maxPriorityFeePerGas: 1500000000n, // 给验证者的小费
  chainId: 1,                  // 防跨链重放
  // ...签名相关: v, r, s
}
```

**`data` 是灵魂**:
- 转账给 EOA → `data` 为空
- 调用合约函数 → `data` = `函数选择器(4字节) + 编码后的参数`
- 函数选择器 = `keccak256("transfer(address,uint256)")` 的前 4 字节
- 部署合约 → `to` 为空,`data` = 字节码

> 你在钱包里看到"这笔交易在调用 approve",就是因为钱包解析了 `data` 的前 4 字节。

## 4. 交易生命周期(核心!)

```
① 构造      你在前端/脚本里组装交易字段
      ↓
② 签名      用私钥对交易哈希签名(v, r, s)→ 证明"是我授权的"
      ↓
③ 广播      通过 RPC 节点发到 P2P 网络
      ↓
④ 进入 mempool   所有待打包交易在这排队(公开可见!)
      ↓
⑤ 被选中 & 打包   验证者按 gas 高低排序,挑进区块
      ↓
⑥ 执行     EVM 逐条执行机器码,改变状态
      ↓
⑦ 共识 & 出块  区块被链接、广播、确认
      ↓
⑧ 最终性   达到 N 个确认后,回滚概率极低(finality)
```

### 每步的"坑"

| 阶段 | 常见问题 |
|---|---|
| ② 签名 | 签名错了 → 交易被拒;`chainId` 不对 → 跨链重放风险 |
| ④ mempool | **所有待处理交易公开可见** → 这就是抢跑(front-running)/ MEV 的温床 |
| ⑤ 打包 | gas 给小了 → 一直 pending;网络拥堵 → 要么加钱要么等 |
| ⑥ 执行 | 合约 `revert` → 交易失败,但 **gas 已经花了**! |

### 🔴 最反直觉的一点

**交易失败 ≠ 不花钱。**

如果 EVM 执行到一半 `revert`,状态全部回滚(像是没发生),但**你已经消耗的 gas 不退**。因为验证者确实为你做了计算。

> 所以合约开发里 "省 gas" 不只是省钱,更是**别让用户白花钱**。

## 5. Gas:链上的"计算费"

**gas = 计量单位**,衡量你消耗了多少计算/存储。
**gas × gasPrice = 你付的 ETH**。

### EIP-1559(现在的主流模型)

```
实际每 gas 花费 = base fee + priority fee
```

- **base fee**:网络根据拥堵自动调整,**被销毁**(不是给验证者)。
- **priority fee(小费)**:给验证者,你加得越多越容易插队。

另外你设定 `maxFeePerGas`(总上限)。如果 base fee 涨太高超过你的上限,交易就一直 pending。

### 为什么简单转账固定 21000 gas?

`21000` 是**最基础的交易开销**(签名验证 + 转账)。任何合约调用都比这贵。

**gas 都花在哪:**
- `SSTORE` 写存储:贵(2万 gas 起),尤其从 0 改成非 0
- 读/写纯计算:便宜
- 首次给一个地址转 ETH:更贵(要创建账户)

> 优化 gas 的核心思路:**少写存储、少循环、别在链上存大数组。**

## 6. EVM 执行模型(够用版)

- EVM 是**栈式虚拟机**,逐条执行 opcode。
- 三种"内存":
  - `storage` — 持久化,贵,上链
  - `memory` — 执行期间的临时内存,便宜,函数结束就没了
  - `calldata` — 调用传入的只读数据,最便宜
- 三种"终止/报错":
  - `require(cond, "msg")` — 条件不满足就 revert,**退还剩余 gas**,错误信息给用户看
  - `assert(cond)` — 用于"不该发生的内部错误",失败也 revert(以前会耗尽 gas)
  - `revert("msg")` — 直接回滚

**状态回滚规则:** 只要 revert,交易内所有状态修改全部撤销 —— **但 gas 不退**(见第 4 节)。

## 7. L1 / L2 / 最终性

- **L1(Ethereum 主网)**:最安全,最贵,最慢(约 12s 一个块)。
- **L2(Arbitrum / Optimism / Base)**:在 L1 之上扩容,便宜几十上百倍,最终性靠 L1 背书。
- **确认数**:交易进块 ≠ 绝对安全。块被重组(reorg)时可能被拿掉。交易所通常等 N 个确认。
- **你开发时**:用测试网(Sepolia)+ L2 练手,几乎零成本。

## 8. 对测试工程师的三个直接启示

1. **失败也是最贵的成功**:链上交易失败照样扣 gas。所以"错误路径测试"和"成功路径测试"一样值钱 —— 这正是你的主场。
2. **边界即攻击面**:nonce 跳号、gas 上限、重入、溢出 —— 链上的 bug 直接等于钱。
3. **可观测性弱**:链上出问题很难"加个日志重跑"。所以**测试必须前置**,这也是 Foundry fuzz/invariant 存在的意义。
